01

The brief, and the scope of v1

Borland Descent is a browser-based, smartphone-first generative music & visual experience — and the minimal studio used to author it.

The reference point is Brian Eno's generative apps (Bloom, Trope), pushed darker, more personal, more immersive, and crucially bidirectional: the sound shapes the image and the image's measured energy shapes the sound. It is a living collaboration between two people in different cities, so the tooling has to make authoring a shared, version-controlled act — not a private session in an opaque editor. That single fact drives more of the architecture than anything aesthetic.

→What this repository is

This is v1: the creative loop — the smallest thing that lets us compose and design real scene content and immediately hear and see it change. One engine; one or two continuous generative scenes; a zoom gesture mapped to a position along an emotional arc; a handful of real audio↔visual modulation routes; a studio that edits scene parameters and those routes live; and lossless save/load of the work as JSON.

→What it deliberately is not

There is no backend, no auth, and no automatic scene-to-scene transitions yet. This is not an oversight to apologise for — it is the plan. The riskiest, most defining question for a project like this is “does the creative loop actually feel good to work in?” Everything else (accounts, hosting, sharing) is comparatively well-understood plumbing. So v1 spends its complexity budget entirely on the loop, and sequences the rest behind clean seams (see §6).

Build the part that might not work first. The plumbing can wait; the feel cannot.
02

The shape of the system

Three things and the lines between them. A Patch holds the authored piece. An Engine renders it. Two front-ends — the player and the studio — instantiate the same engine with the same patch. The studio additionally edits the patch and exports it; collaboration happens through git.

Reading this top-down is the descent the work is named for: the surface is what you touch, the truth is underneath. Reading it bottom-up is the dependency order — the Patch and its store know nothing of the engine; the engine knows nothing of React; React knows nothing of how you choose to host it.

03

The six load-bearing rules

The non-negotiables — each a constraint accepted on purpose for what it guarantees downstream, and most enforced mechanically rather than by good intentions.

Rule 1

The Patch is the single source of truth

A zod-validated JSON document describes the whole piece — DNA, scenes, the audio and visual graphs, and the modulation matrix. The studio edits it; the engine renders it; nothing else holds authored state.

Why
If authored state lived in React component state, or scattered across engine objects, then “the piece” would be un-saveable, un-diffable and un-shareable. Making one serialisable document canonical is what makes save/load lossless and git the collaboration medium — the founding requirement.
Trade-off
Every authored thing must be expressible as plain data. No clever closures or live object references in the authored layer. That discipline is the point.
Enforced by
A single schema in patch/schema.ts; the engine takes a Patch and never invents state the patch cannot describe; the studio round-trips it on export.
Rule 2

The engine is framework-agnostic

It imports only tone, three and zod — never React, never Vite. The player and studio both instantiate the same Engine with the same Patch.

Why
The engine is the asset with a ten-year life; React 19 is a detail of this year. A clean boundary means a future native shell, a different UI framework, or a headless render can reuse the engine untouched — and keeps it testable as plain TypeScript.
What it rejects
The tempting shortcut of reaching into a React context from inside audio code. Convenient once, a tangled dependency forever.
Enforced by
Two independent guards: the engine's package.json lists only tone/three/zod, and an ESLint no-restricted-imports rule fails the build if anything under packages/engine imports react or vite. Belt and braces, because this is the rule most likely to be broken under deadline pressure.
Rule 3

Persistence is reached only through PatchStore

v1 ships a JsonPatchStore (fetch a committed JSON file; export is a browser download). A reactive backend later implements the same interface, unchanged.

Why
It lets v1 ship with zero backend while guaranteeing that adding one (Convex is the intended target) is an implementation swap, not a refactor. The load / save / list? / subscribe? shape already anticipates a live, multi-user backend.
Trade-off
In v1, save deliberately throws: you export from the studio and commit the file. Slightly manual, but it means “saving” is a git commit with full history and review — exactly right for a two-person collaboration today.
Enforced by
Nothing in the engine or studio imports a concrete store; they depend on the PatchStore interface in patch/store.ts.
User samples
The same seam shape covers user-loaded samples. The Patch references a sample by id (node.sampleId); the audio binary lives in a runtime SampleStore (an in-memory cache over IndexedDB today; a backend later) — never in the JSON. A deliberate carve-out from “the document contains everything”: embedding binary audio as base64 would bloat the patch and defeat lossless text round-tripping, so the JSON stays small and an export-with-samples bundle is the sharing follow-on. The same id-by-reference rule covers a convolution reverb's impulse response (node.ir → an IR WAV such as an Open AIR cathedral); a generated hall IR is synthesised when none is set, so the patch alone always renders.
Rule 4

Everything modulatable is a typed, addressable port

A PortRef is a stable string "nodeId.portName". Ports have a kind — scalar · unipolar · bipolar · trigger · vector — and a direction. The matrix only connects type-compatible ports.

Why
Modulation needs a vocabulary that is both stable in the saved document and richly typed at runtime. A string address survives serialisation and git diffs; the kind lets the matrix refuse nonsense instead of silently producing garbage.
Design detail
Node ids are dot-free by schema, so the dot in a PortRef is always unambiguous. Numeric kinds interoperate — the matrix scales and curves between them — while trigger and vector only pair with their own kind. Pragmatic where it is safe, strict where it is not.
Enforced by
The schema validates the PortRef format; isCompatible() in core/ports.ts gates every route; a registry maps abstract refs to live engine objects at build time.
Rule 5

Audio and visual share one clock

A single Transport over Tone's transport. Audio events schedule against its look-ahead; the visual rAF loop reads transport time each frame.

Why
Two clocks drift, and drift between sound and image is exactly the thing that breaks immersion. One clock means the picture is always referring to the same time the music is keeping.
Honest limit
The visual loop is related to audio time, not sample-accurate — it reads transport seconds per frame rather than being driven by the audio thread. For a generative ambient piece that is the right trade: cheap, smooth, and close enough that the eye never catches the seam.
Enforced by
All time flows through core/transport.ts, using the Tone v15 getter API (Tone.getTransport()) rather than a second timer.
Rule 6

Control-rate and audio-rate modulation are not interchangeable

A route's rate field records which it is, and they are wired by entirely different mechanisms.

Control-rate

Evaluated once per frame and smoothed. Used for visual uniforms, reverb/filter moves, and all audio→visual links. Cheap, inspectable, smoothed against frame jitter.

Audio-rate

Wired once as a native Tone.Signal connection (an LFO or envelope into a cutoff or amp) and never written per frame. Sample-accurate, zero per-frame cost.

Why
This is the decision that keeps the engine both smooth and correct. Writing an audio-rate signal from JavaScript every frame produces zipper noise and wastes the audio thread; evaluating a per-frame control value as if it were an audio signal makes it untestable and jittery. Naming the rate in the document forces the author — and the engine — to be honest about which world each route lives in.
Enforced by
The Matrix branches on rate: audio routes become a Tone.Gain between two native nodes at setup; control routes are accumulated and smoothed in the frame loop. The two paths never cross.
04

Finer decisions, and why

The rules set the frame. These are the smaller, less obvious choices that make the thing actually pleasant — and safe — to work in.

→Schema-first, with forward compatibility built in

The zod schemas are canonical; the TypeScript types are inferred from them with z.infer, so the two can never drift. Three small choices keep older patches loading as the document evolves:

  • the top level is a loose object, so an unknown future field is tolerated rather than rejected;
  • meta.version carries the document schema version;
  • new fields use .default(), so a patch written before the field existed still validates.

This matters because the canonical piece is committed to git and edited over months. A schema that rejected last week's patch would make the format hostile to the very collaboration it exists to serve. There is also a graceful-degrade path: if the patch is missing or invalid, the player falls back to a bundled default and still runs — never a blank screen.

Bounded inputs. Import is an untrusted path, so the schema also carries hard ceilings on anything that allocates: maxPolyphony ≤ 24 (the phone performance budget), subdivisions ≤ 32, humanizeMs ≤ 250, vector params ≤ 4096 entries. A patch is authored data, but a malformed or hostile one must degrade to a validation error — never a frozen tab.

→Sequences enter the Patch — and migrations enter with them (schema v2)

The sequencer's authored state — per-scene step patterns with swing, per-step probability, ratchets and port-target tracks — is serialised in the Patch like any route (patch/schema.ts, sequences), because rule 1 admits no second home for authored state. Two structural choices ride along:

  • Real migrations. meta.version stops being decorative: patch/migrate.ts lifts older documents step-by-step (v1→v2 adds sequences: []) before zod validation, and every load path goes through it. Defaults handle missing fields; migrations handle reshaped ones. The steps are additive and idempotent, so a patch saved last month keeps loading forever.
  • One clock, formalised. The transport grows into an explicit façade (core/transport.ts, TransportClock): bpm, time signature, musical position and a scheduleWindow lookahead pump that hands consumers the exact AudioContext time of each window — so the sequencer schedules sample-accurately through the same Tone transport the composer and the visual loop already read (rule 5), never via setTimeout. Control-rate writes gain a shared dezipper (core/params.ts, smoothWrite) so per-frame parameter moves glide instead of stepping.

→Determinism that fixes decisions, not samples

Composition is driven by a seeded RNG (mulberry32, with djb2 string hashing), so a given meta.seed reproduces the same compositional choices — the same notes, rhythms and parameter picks. It deliberately does not attempt bit-identical audio: live analyser values still vary run to run. Pinning decisions makes the piece reproducible enough to author against and to test; chasing bit-identical output would fight the Web Audio clock for no creative gain. The seed pins the score, not the performance.

→The matrix: refuse, sum, and smooth — deterministically

The modulation matrix is where the most subtle bugs hide, so three behaviours are defined explicitly:

  • Refuse, don't guess. A route to an unknown port, or between incompatible kinds, is warned about and dropped — never silently summed or wired.
  • Sum contributions, but smooth deterministically. When several control routes share one target, their contributions add — but a single smoothing time governs the result: the slowest (max) across those routes. An earlier “first route wins” policy meant reordering routes could change how the piece felt. Feel must not depend on array order.
  • Relax to base when a route disappears. When the studio removes or disables a route live, its target snaps back to its base value. Without this, the target would freeze at its last modulated value. That “studio-edit freeze” was a real bug; the fix is now covered by a test.
  • Amount is a fraction of the target's range. A control route's contribution is curve(source) × amount × (max − min) of the target port (span 1 when a port declares no bounds). The schema caps amount at ±1, so before this normalisation no route could move a port whose range exceeded ~1 — the shipped zoom→cutoff route modulated an 80–12 000 Hz filter by ±1 Hz, silently. Normalising makes ±1 mean “the full sweep” on every port, identical for a fog amount and a filter cutoff; visual ports (0–1) are unchanged. Covered by a test.
  • Routes may be scene-scoped. A route can carry an optional sceneId: the engine only wires it while that scene is active. Untagged routes stay global and a route to a port the current scene doesn't expose is still safely dropped — but “dropped” is now stated intent rather than noise. Dropped-route warnings fire once per page session (repeats demote to console.debug): the same message per Matrix rebuild — StrictMode double-builds times a crossfade per scene — was hundreds of identical console lines saying nothing new.
// a modulation route, as stored in the Patch
{
  source:  "bassMeter.level",   // an OUTPUT port
  target:  "field.fog",         // an INPUT port
  amount:  0.8,                  // bipolar scale
  curve:   "sCurve",             // linear | exp | log | sCurve | invert
  rate:    "control",            // control (per-frame) | audio (native)
  smoothing: 50                   // ms — max across routes to one target wins
}

Triggers became first-class sources (V2). The audio feature layer (audio/features.ts, pure and headless-tested) exposes eight log-spaced envelope-followed bands, spectral flux, and an adaptive onset detector whose port kind is trigger. The compatibility rule gained one deliberate asymmetry: a trigger SOURCE may drive any numeric target — the matrix converts the pulse into a decaying envelope whose release is the route's smoothing, and such routes bypass per-target smoothing so the attack stays instant — while nothing numeric may ever drive a trigger input. One event, one trigger, one sharp visual gesture: the Ikeda-tight mapping, serialised like any other route.

→The audio graph is topology-in-the-patch (not topology-in-code)

The Patch document carries a full audioGraph.nodes + connections list. The engine builds the Tone audio graph from that data — not from hard-coded wiring in audioEngine.ts. An EffectModule registry maps each node's kind and moduleId to a builder that creates the right Tone node, registers its ports, handles async init (convolution IR, tape worklet), and connects via the connection list. Adding an effect therefore means adding a node to the patch and optionally registering a new moduleId — not editing the engine. This is the proper fulfilment of Rule 1: the topology is authored state, not implementation detail.

→Live editing without rebuilding the audio graph

In the studio you can move a slider or rewire the matrix and hear it immediately, without the audio cutting out. Edits flow through engine methods (setInputBase, setRoutes, setSequences) that mutate the running graph in place and keep the working patch in sync for export. The React lifecycle is keyed so ordinary edits do not tear the engine down — only a structural change (importing a patch, switching to a structurally different scene) bumps a reloadToken to force a clean rebuild.

→The engine as a host; a scene as a unit

The engine does not own a scene's audio and visuals directly — it hosts them. A SceneInstance bundles one scene's audio graph and visual stack and registers their ports; the Engine keeps only the shared, scene-independent concerns — the one transport, the gesture input, the port registry, the modulation matrix and a single master bus — and drives the active instance each frame. Each scene feeds that master through its own output gain; today exactly one does. But that is precisely what turns the two deferred features needing a scene to be a movable unit — a crossfade that runs two scenes at once, and an arc that hands off from one scene to the next — into the host holding a second instance and ramping the two gains against each other, rather than a rewrite of the engine's core. Draw the line before code leans on the engine owning a single scene, not after.

→The audio lifecycle, and the still first frame

There is exactly one AudioContext for the page — Tone owns it, and we never construct a second (Safari caps them at roughly four). It can only be unlocked from a user gesture, so the player opens on a still, inviting first frame: visuals and gesture are built up front and rendered once; audio is built only when you tap to begin. On iOS the context can be interrupted by backgrounding, so there is an explicit “tap to resume” path. These are the difference between “it works on my laptop” and “it works on a phone on the train”.

→Surviving React StrictMode and hot reload

The engine owns real, disposable resources (audio nodes, a WebGL context, event listeners). React 19 StrictMode double-mounts in development and Vite hot-reloads modules, so the engine is created and disposed symmetrically inside an effect — not guarded by a lazy ref, which is unsafe under StrictMode — and dispose() unwinds everything it built. Getting this wrong leaks audio voices and WebGL contexts until the tab dies; getting it right is invisible, which is the goal.

→One renderer, many worlds (the visual-module contract)

The visual side was rebuilt around two ideas (see docs/VISUAL-REBUILD.md). First, ONE WebGLRenderer + EffectComposer for the whole engine (visual/host.ts): a scene contributes a layer module, not a pipeline, and a crossfade renders the outgoing and incoming layers into two pooled targets mixed by a blend pass — one bloom, one grain, one output regardless of scene count, where previously every transition ran two complete pipelines. Second, every module exports a static VisualModuleDescriptor — its parameters as schema — from which the registry bindings, the studio panels and the routing-target list are generated (visual/moduleDescriptor.ts). Adding a visual module therefore touches no control or audio plumbing: one file exporting { descriptor, create } plus a registry line. Per-scene visualParams carry each scene's parameter bases and its post grade (bloom strength/radius/threshold, grain), lerped across crossfades, so seven scenes own seven looks within one pipeline.

→Designed to a real phone

The performance budget is a concrete device: a mid-range phone at a 390 px viewport, iOS Safari. Several choices fall straight out of that target:

  • fragment shaders are favoured over heavy geometry, and device pixel ratio is capped at 2;
  • voices are capped (~24) and the FFT size kept small (512–1024);
  • the frame loop suspends when the tab is backgrounded, to save battery — a ~4 Hz fallback tick keeps audio handover, tempo drift and modulation alive while hidden (and engages even if the engine starts hidden);
  • prefers-reduced-motion is honoured — when set, the visual time is frozen so the picture holds still rather than animating;
  • the entry bundle carries only React and the player shell (~60 kB gzip): tone + three live in a separate chunk reached ONLY by dynamic import, loading behind the veil instead of blocking first paint, and the studio is a lazy route a listener never downloads.

→Compositional decisions kept pure

The generative composer is split in two: a pure, deterministic decision function (seeded RNG in, note decisions out) and the Tone scheduling that plays those decisions. The split lets the musically interesting logic — how the DNA motif walks the scale, how arc density gates the pad, how the bass anchors the bar — be unit-tested headlessly, with no audio hardware. The CI smoke test exercises exactly this surface.

Structure over statistics. The decision function carries explicit musical structure rather than uniform randomness: a slow harmonic cycle (i → VI → iv → v as scale degrees, one chord per bass period) that the bass voice-leads through; an 8-bar phrase envelope that arcs the pad's velocity and thins notes at phrase ends; occasional dyads whose intervals come from the scene's harmonicGuardrails.allowedIntervals. The arc macros now reach the music directly — rhythmicWeight raises bass weight and passing-note likelihood, dissonance loosens chord gravity and unlocks the pungent dyad intervals, and darkness sinks the pad register an octave in the deep half — so the descent changes what is played, not just how busy it is. All of it remains pure and seed-deterministic.

Tempo and groove belong to the arc too. The transport's BPM follows bpmAt(dna.tempoRange, arc) — the surface takes the range's top, the deep its floor, smoothed through a ~2.5 s lag so scrubbing never jerks the clock. The motif's rhythm array is its duration pattern in steps (a recurring rhythmic identity, not dice), quarter-grid steps are favoured and lightly accented over off-beats, and off-beat eighths sit a touch late — a swung lilt that deepens with rhythmicWeight while bass downbeats stay straight. One consequence is owned explicitly: sequences compute their grid from ctx.bpm, so tempo drift re-grids them between lookahead windows; the scheduler keeps a per-sequence high-water mark and drops re-scanned events, trading at worst a skipped step while actively scrubbing for never double-firing.

05

How we know it works

The CI gate tests the pure-logic surface — the parts where a bug is silent and expensive — and is honest about what a headless runner cannot reach.

jsdom cannot run Web Audio or WebGL, so the engine's audio and visual backends are exercised behind interfaces, not for real. That is a deliberate boundary, not a gap: the value is in testing the logic that decides what to render, which is exactly the logic kept pure for this reason. Three pillars:

  • Determinism — the seeded RNG reproduces the same sequence, so a seed reproduces a piece.
  • Schema round-trip — a patch validates, serialises and re-validates losslessly; defaults apply forward-only.
  • Matrix behaviour — type-incompatible routes are dropped and never write; smoothing across routes to one target is order-independent (max wins); a removed route relaxes its target back to base.

npm run check runs the full gate — strict TypeScript across both packages, ESLint (including the framework-agnostic boundary), and Vitest — and CI runs the same plus a production build on every push and pull request. A real-audio browser-mode suite (Playwright) is a documented later option for behaviour only a real audio context can show; it is intentionally not the gate today, because a flaky browser test that blocks merges would cost more than it catches.

06

What is deferred, and the seams that keep it cheap

Scope was cut deliberately. The test of a good cut is whether the deferred thing is a swap later, or a rewrite. Each of these is a swap, because the seam already exists.

A reactive, multi-user backend deferred
The PatchStore interface already has the shape a live backend needs (load / save / list / subscribe). v1's JsonPatchStore and a later Convex store are interchangeable; nothing above the seam changes.
Scene-to-scene transitions deferred
The Patch schema already models a SceneTransition (crossfade / morph / none, with duration), and the runtime now has the unit it needs: the engine hosts a self-contained SceneInstance. A crossfade becomes the host holding a second instance and ramping a blend — not a re-plumb.
The seven-scene arc, played end-to-end shipped
The seven scenes are authored — each a distinct synth + shader module tiling its arcRange slice from surface to trench — and §18.1 arc-driven traversal now plays them: in the player the arc position selects the scene, swapping the active SceneInstance in place as you descend (one scene live at a time, so ports never collide; the studio keeps manual selection). The one rough edge — a brief gap while the next scene's reverb builds — is what the boundary crossfade above smooths next.
Accounts, hosting, sharing deferred
Because the engine is framework-agnostic and the output is a static build, the player hosts as plain static assets with an SPA fallback, and auth can wrap the studio later without touching the engine.

The thread running through all four: the constraints in §3 are what make the omissions safe. A single source of truth, a clean engine boundary and a persistence seam are precisely the things that turn “we'll add it later” from a hope into a plan — and the seven-scene arc, now playing for real with the modulation matrix and Patch schema untouched, is the first of them to prove the seam holds.

→If you change one thing, read this first

The two rules most expensive to break are Rule 1 (the Patch is the truth) and Rule 2 (the engine imports no framework). Almost every other decision is downstream of those two. The ESLint boundary will stop you breaking Rule 2 by accident; nothing but care will stop you breaking Rule 1 — so when adding a feature, ask first: “can this be expressed in the Patch?”
